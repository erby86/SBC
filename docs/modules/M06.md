# M06 — นำเข้า AP จาก controller

ตาม modules-by-gate-v2: ตัวเชื่อม UniFi, Omada, LINK (อ่าน) → `net.devices` role ap + `managed_by` + `external_refs` (MAC)

**เสร็จเมื่อ:** AP 132 ตัวอยู่ในฐาน; AP ที่ยังไม่ระบุห้อง/ชั้นขึ้นรายการให้คนเติม

## ส่วนที่ 1: UniFi — โค้ดเสร็จ

controller: UniFi OS Server 5.1.42 (Network 10.6.106) บน Ubuntu `https://172.16.0.30:11443`, site ภายใน `02gt1bcf` (ชื่อแสดง SB-SCHOOL; site `default` ว่าง)
ผู้ใช้ `View Only` แบบ local (role `readonly`) — ไม่มีเมนู API key ในรุ่นนี้ จึงใช้ username/password

| ไฟล์                                  | หน้าที่                                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------------------------- |
| `apps/worker/src/connectors/unifi.ts` | login `/api/auth/login` (cookie `TOKEN`) แล้วอ่าน `/proxy/network/api/s/<site>/stat/device` |
| `apps/worker/src/jobs/unifi-aps.ts`   | งาน `unifi-aps` ทุกชั่วโมง (system `unifi`, actor `worker:unifi-aps`)                       |

กติกา:

- เอาเฉพาะ `type = uap`; หาอาคาร/ชั้นตามลำดับ:
  1. ชื่อ AP (`NAME_RULES`): รูปแบบกลาง `<รหัสอาคาร>-<ชั้น>-<ลำดับ> [ข้อความ]` ใช้ได้ทุกอาคาร (เช่น `SP-3-1 Canteen`, `BB-1-1 ITB`, `I1-2-3`); รูปแบบเดิม `8SFL<ชั้น>-<n>` → s8, `A<ชั้น>-<n>` / `AF<ชั้น>-<n>` → ba, `BFL<ชั้น>-<n>` / `BF<ชั้น>-<n>` → bb, `UAP-AC-7AP<ชั้น>F` → ba
  2. สวิตช์ประจำชั้นที่ AP ต่ออยู่ (`FLOOR_SWITCH_RULES`): `US<n>BFL-<ชั้น>` → bb ชั้นนั้น, code ลงท้าย `p<พอร์ต>` เช่น `ap-bb-4-p4` — ไม่ใช้สวิตช์หลักของอาคาร (`US24AFL-4` = m-a4) เพราะสายลากหลายชั้น
  3. ไม่ได้ทั้งสองทาง → `unplaced_ap`
- เก็บสวิตช์/พอร์ตที่ต่อไว้ใน `attributes.unifi_uplink` (`{device, port}`) และที่มาของชั้นใน `attributes.floor_from` (`name`/`uplink`) — ใช้ทำ uplink ในผังภายหลัง
- AP ใหม่ → `net.devices` code `ap-<อาคาร>-<ชั้น>-<n>` (ชนกับ code เดิม รวมที่ลบแล้ว → ต่อท้าย MAC 4 ตัว), `floor_id`, `poe_powered`, model จาก `catalog.models` (สร้างให้ถ้าไม่มี), `managed_by` = `ctl-unifi`
- controller เองเป็นอุปกรณ์ `ctl-unifi` (role controller) สร้างครั้งแรกที่รัน
- จับคู่ของเดิมด้วย MAC (`external_refs` system `unifi`, `external_id` = MAC, `external_key` = ชื่อใน UniFi) แล้วด้วย `net.devices.mac` (กรณีลงทะเบียนมือไว้ก่อน)
- ของเดิม: อัปเดต hostname, IP, firmware, model, managed_by เมื่อค่าต่างเท่านั้น — **ไม่ย้ายชั้น/ห้องที่คนกำหนดแล้ว**
- `sync.issues` (เปิดครั้งเดียวต่อ MAC, ปิดเองเมื่อหาย):
  - `unplaced_ap` — ชื่อไม่บอกชั้น (= รายการให้คนเติม) วิธีแก้ที่แนะนำ: ตั้งชื่อใน UniFi ตามรูปแบบข้างบน
  - `ip_conflict` — IP ซ้ำกับอุปกรณ์อื่นในทะเบียน (ไม่ใส่ IP ให้ AP นั้น)
  - `missing_in_controller` — AP ที่เคยนำเข้าแต่ไม่อยู่ใน UniFi แล้ว (ไม่ลบเอง)
- TLS: controller ใช้ใบรับรองที่ออกเอง → pin ใบรับรองด้วย `UNIFI_CA_FILE` (ตรวจใบรับรอง ข้ามแค่ชื่อ host); `UNIFI_TLS_INSECURE=true` ใช้ทดสอบเท่านั้น; ไม่ตั้งทั้งคู่ → งานปิดพร้อมคำเตือน
- env (worker เท่านั้น): `UNIFI_URL`, `UNIFI_USERNAME`, `UNIFI_PASSWORD`, `UNIFI_SITE`, `UNIFI_CA_FILE` (ใน container: `/run/noc-certs/…` = `/opt/sbc-noc/certs` บนเครื่อง, read-only)

ข้อมูลจริง 2026-10-03: AP 80 ตัว (online 78), รุ่น U7LR, U7MSH

- อ่านจากชื่อ 44 ตัว (8SFL ×28, A/AF, BFL/BF, UAP-AC-7AP<ชั้น>F ×4), จากสวิตช์ `US16BFL-2/4/6` อีก 14 ตัว (`AC LR`) → คาด 58 ตัว
- เหลือ 22 ตัวต้องตั้งชื่อใหม่ใน UniFi (ผู้ใช้ยืนยันตำแหน่ง 2026-10-03):
  - `AC Mesh` ×12 = ICET1 ชั้นละ 4 → `I1-<ชั้น>-<n>`
  - `AC LR Canteen` = อาคารกีฬา ชั้น 3 → `SP-3-1 Canteen`; `AC LR ITB` = อาคาร B ชั้น 1 → `BB-1-1 ITB`
  - `UAP-AC-LRA1/8/9/12/13/15/16`, `AC LRA` (ต่อ `US24AFL-4` = สวิตช์หลักอาคาร A) → รอผู้ใช้บอกชั้น

ทดสอบ (PostgreSQL 16 + UniFi จำลอง): วางชั้นถูก, code ชนกับ `ap-ba-2-1` ที่ลบแล้ว → `ap-ba-2-1-0001`, รอบสองไม่เขียนอะไร (audit ไม่เพิ่ม), ชั้นที่คนแก้ไม่ถูกย้าย, เปลี่ยนชื่อแล้ว issue ปิดเอง, AP หายขึ้น `missing_in_controller`

## ย้าย controller ไป UDM Pro Max (แผนไว้ล่วงหน้า)

UDM Pro Max เป็น UniFi OS เหมือนกัน — API (`/api/auth/login`, `/proxy/network/api/...`) เดิม จึง**ไม่ต้องแก้โค้ด** เปลี่ยนแค่ค่าตั้ง:

1. ย้ายด้วย backup/restore ของ Network (หรือ "Migrate" ใน UniFi) → AP ย้ายตาม MAC เดิม ทะเบียนจับคู่ด้วย MAC จึงไม่เกิดอุปกรณ์ซ้ำ
2. สร้างผู้ใช้ View Only แบบ local บน UDM ใหม่ (ผู้ใช้ระดับ UniFi OS ไม่มาพร้อม backup)
3. เก็บใบรับรองของ UDM ทับ `/opt/sbc-noc/certs/unifi-ca.pem` (คำสั่ง openssl เดิม เปลี่ยน IP, พอร์ต 443)
4. `dev.env`: `UNIFI_URL=https://<IP UDM>`, `UNIFI_USERNAME`/`UNIFI_PASSWORD` ใหม่, `UNIFI_SITE` (ตรวจด้วย `/proxy/network/api/self/sites` — restore มักคงชื่อเดิม), `UNIFI_CONTROLLER_CODE=udm`
5. `up -d` worker → รอบถัดไป `managed_by` ของ AP ทุกตัวย้ายไป `udm` (อุปกรณ์ `udm` มีในทะเบียนแล้ว สถานะวางแผน) → เปลี่ยน `udm` เป็น active, `ctl-unifi` เป็น retired

กันพลาด: ถ้า controller ใหม่ตอบว่าไม่มี AP เลย (เช่น `UNIFI_SITE` ผิด) งานจะล้มใน `sync.runs` แทนที่จะขึ้น "AP หายจาก controller" ทั้ง 80 ตัว

ทางเลือกภายหลัง: UniFi Network รุ่นใหม่บน UDM มี Integration API แบบ API key (ไม่ต้องใช้รหัสผ่าน) — เปลี่ยนเฉพาะ `connectors/unifi.ts` ถ้าต้องการ
