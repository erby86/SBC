## 2. สิ่งที่เพิ่มในหน้าจอหลัง v2

- ค้นหาแบบรายการผลลัพธ์: จัดกลุ่ม อาคาร → ชั้น → อุปกรณ์, ค้นหลายคำ (ชื่อ, IP, ตึก, ชั้น, ประเภท, รุ่น, VLAN, สถานะ), ยืดหยุ่นการพิมพ์ (อ.1, 8เซียน, sport), ไฮไลต์หลายรายการในภาพ, ค้นด่วน/ค้นล่าสุด, `/` หรือ `Ctrl+K`
- แผนที่ย่อแบบใหม่: กรอบฟ้า = พื้นที่ที่เห็นอยู่ + ลูกศรทิศที่มอง, ✕ ล่ม ▲ เตือน, ชื่อย่อบนตึก, ทิศเหนือ, คำอธิบายใต้แผนที่
- วิธีใช้ในตัว: ปุ่ม ?, แนะนำการใช้งานครั้งแรก 4 ขั้น, คำบอกใบ้วิธีควบคุม, คำอธิบายสัญลักษณ์สถานะติดแถบล่าง
- ISP ใช้ระบบสถานะเดียวกับอุปกรณ์อื่น (ลำแสง, วงคลื่น, ป้ายลอย, รับเรื่องได้, ชิปคลิกได้)
- รับเรื่องแล้วแก้ไข/ยกเลิกได้
- ป้าย "ข้อมูลตัวอย่าง" ติดแถบบนตลอด และบรรทัดกำกับในรายการแจ้งเตือน
- เลย์เอาต์กริด responsive ใหม่ ขนาดทุกส่วนผูกกับตัวอักษรฐาน, ปุ่ม/ชิปสูงตามบรรทัด (ไม่ตัดสระไทย), กันข้อความเลยขอบ, มือถือต่ำกว่า 900px เป็นแผ่นแท็บ
- ข้อความเตือนเมื่อโหลดภาพ 3D ไม่ได้ (เน็ตหลุด / เครื่องไม่รองรับ WebGL)
- สลับโหมดประหยัดอัตโนมัติเมื่อภาพต่ำกว่า 24 เฟรม/วินาที

## 3. บั๊กที่แก้

- บำรุงรักษาถูกนับเป็นเครื่องหายในชิปสรุป
- แผงรายละเอียดค้างข้อมูลเก่าหลังรับเรื่อง/เปลี่ยนสถานการณ์
- คลิกเหตุ ISP แล้วลูก ISP จางเพราะโฟกัสตึกค้าง
- ผลค้นหาหัวข้อกลุ่มซ้ำสลับกัน
- โฟกัสคีย์บอร์ดหลุดทุก 5 วินาทีในรายการแจ้งเตือน
- ปุ่มลัดใช้ไม่ได้บนแป้นภาษาไทย
- ป้ายชื่อตึกหลบกันผิดหลังฟอนต์โหลด/โหมดทีวี
- ภาพแสงเรืองเบลอในโหมดประหยัด
- หมายเหตุรับเรื่องแทรก HTML ได้ (กรองแล้ว)
- ตัวอย่างห้องคอมฯ แสดงเครื่องออนไลน์เกินจำนวนจริง

## 4. ประสิทธิภาพ

- AP 132 ตัว, เส้น AP 132 เส้น และหางแสงไฟเบอร์ราว 220 ก้อน รวมเป็นชิ้นวาดเดียวต่อกลุ่ม (instancing)

- โหมดประหยัด: ปิดแสงเรืองและหางแสง ลดความละเอียด แต่คงลำแสงและวงคลื่นเหตุล่ม

## 5. ทะเบียนอุปกรณ์และพื้นที่ (ฐานข้อมูล)

- การตัดสินใจ: ทะเบียนอาคาร พื้นที่ (LOC) อุปกรณ์ และการเชื่อมต่อ เก็บใน **ฐานข้อมูล** เป็นแหล่งจริงแหล่งเดียว ไม่ใช้ Google Sheet
- ฐานข้อมูลที่ใช้: **PostgreSQL 16 แยก container ชื่อ `sbc-noc-db`** ไม่ใช้ร่วมกับ `sbc-db` (MariaDB ของระบบอื่น) และไม่ใช้ร่วมกับ `sbc-zabbix-db` ฐานชื่อ `sbc_noc`, ผู้ใช้แอปแยกจากผู้ใช้ migration, volume ของตัวเอง, ไม่เปิดพอร์ตออกนอก docker network
- สำรองข้อมูล: pg_dump รายวันเก็บ 14 วัน + รายสัปดาห์เก็บ 8 สัปดาห์ เข้าที่เก็บ backup เดิม และทดลองกู้คืนทุกเดือน
- extension: `pg_trgm` (ค้นหาแบบคลาดเคลื่อนได้), เผื่อ `postgis` ภายหลังถ้าวาดผังชั้นจากแบบแปลนจริง
- ออกเลข LOC ใหม่จากฐานข้อมูล (ลำดับเลขกลาง ไม่ชนกัน) แก้ปัญหาเลขชนที่ค้างจาก v3
- Google Sheet `SBC_NOC_ทะเบียนอุปกรณ์และพื้นที่_v1` ที่ทำไว้ ใช้เป็น **ข้อมูลตั้งต้นนำเข้าครั้งเดียว** (LOC 173 รายการ, อุปกรณ์ 50 แถว) หลังนำเข้าแล้วเลิกใช้แก้ไข
- SBC ASSET ยังเป็นเจ้าของทะเบียนเครื่องคอมพิวเตอร์; ฝั่ง NOC นำเข้า/ซิงก์รายการ LOC จาก SBC ASSET และเมื่อ SBC ASSET ย้ายไปฐานข้อมูลของตัวเอง ให้ใช้ตาราง LOC ร่วมกัน
- AP ทั้ง 132 ตัว นำเข้าจาก UniFi / Omada / LINK controller เข้าตารางอุปกรณ์

โครงตารางสรุปตั้งต้น (ฉบับปัจจุบัน 61 ตาราง ใน 10 schema อยู่ใน `sbc-noc-schema-design-v1.2.md` และ `sbc-noc-schema-v1.1.sql`)

| ตาราง | เก็บอะไร | คอลัมน์หลัก |
|---|---|---|
| `buildings` | อาคาร | code (sp, i2, i1, b1, b2, s8, ba, bb), name, asset_name, floors, rooms_per_floor, form, geometry (ตำแหน่ง/ขนาด/มุมในผัง 3D) |
| `locations` | ห้อง/พื้นที่ (LOC) | loc_code, building_code, floor, name, corridor_order, area_type, has_rack, source (SBC ASSET / NOC), registry_count |
| `devices` | อุปกรณ์เครือข่าย | id, display_name, zabbix_host, zabbix_hostid, role, model, ip, building_code, floor, loc_code, uplink_device_id, link_type, vlan, asset_tag, data_status, pos_u, pos_v |
| `links` | เส้นไฟเบอร์และเส้นพิเศษ | id, from_device, to_device, media, color, route_hint |
| `lab_rooms` | สรุปห้องคอมฯ | loc_code, pc_total (จาก SBC ASSET) |
| `audit_log` | ประวัติการแก้ไขทะเบียน | who, when, table, row, before, after |
| `sync_runs` | ผลการซิงก์กับ Zabbix / SBC ASSET / controller | source, started, finished, changed, errors |

## 6. เรื่องที่ยังเปิดอยู่

- LOC-187 (ห้อง server) ออกไว้ในไฟล์ Sheet ตั้งต้น ต้องยืนยันเลขอีกครั้งตอนนำเข้าฐานข้อมูล และตกลงกับ SBC ASSET ว่าใช้ตาราง LOC ร่วมกัน
- จำนวนห้องต่อชั้นและแบบอาคาร (ปรับขนาดอาคาร)
- อุปกรณ์ที่อาคารกีฬาชั้น 3, การเชื่อมระหว่าง main สองตัวของ ICET1, ชนิดสาย ICET2 → อาคารกีฬาชั้น 1
- วิธีบันทึกผู้รับเรื่องใน Zabbix และวิธีเข้าสู่ระบบของ sbc-noc
- ยังไม่ได้ทดสอบภาพจริงบนจอทีวี/mini PC และมือถือหลายรุ่น

## 7. เครื่องมือ ภาษา และเทคนิค (เลือกเพื่อต่อยอดระยะยาว)

หลักการเลือก
- **ภาษาเดียวทั้งระบบ: TypeScript** ทั้งหน้าจอ ส่วนหลังบ้าน งานซิงก์ และสคริปต์ ทีมเรียนครั้งเดียวใช้ได้ทุกส่วน, type ร่วมกันระหว่างหน้าจอกับ API
- เลือกเครื่องมือที่ **ใช้กันแพร่หลาย มีรอบ LTS ชัดเจน และเป็นมาตรฐานเปิด** (SQL, REST/OpenAPI, OIDC, Docker) เพื่อให้เปลี่ยนคนดูแลหรือเชื่อมระบบใหม่ได้ง่าย
- โครงแบบ **monorepo** ให้ SBC ASSET หรือระบบอื่นของแผนกไอทีมาใช้แพ็กเกจกลาง (ทะเบียน LOC, การเข้าสู่ระบบ, UI) ร่วมกันได้ภายหลัง

**โครงสร้างโค้ด (monorepo `sbc/sbc-noc` ใน Gitea)**
- pnpm workspaces + Turborepo
- `apps/web` หน้าจอ, `apps/api` ส่วนหลังบ้าน, `apps/worker` งานซิงก์
- `packages/db` (schema + migration), `packages/shared` (zod schema, type, ค่าคงที่ เช่น รหัสอาคาร), `packages/ui` (ชิ้นส่วนหน้าจอใช้ซ้ำ)
- บันทึกการตัดสินใจเป็น ADR ใน `docs/adr` (เช่น ทำไมแยก PostgreSQL, ทำไมใช้ REST)

**หน้าจอ (`apps/web`)**
- TypeScript + React (รุ่นปัจจุบัน) + Vite สำหรับแผงต่างๆ หน้าจัดการทะเบียน และหน้าในอนาคต
- ภาพ 3D: Three.js (รุ่นโมดูลปัจจุบัน) แยกเป็นโมดูลฉากที่ไม่ขึ้นกับ React (React ส่งข้อมูลเข้า, ฉากวาดเอง) คงเทคนิค InstancedMesh, bloom ปิดได้, โหมดประหยัด
- ดึงข้อมูล/แคชฝั่งหน้าจอ: TanStack Query, ข้อมูลสดผ่าน WebSocket
- UI: CSS ของระบบเองตามดีไซน์ต้นแบบ (ตัวแปรสี/ขนาดชุดเดียว) + Radix UI สำหรับชิ้นที่ต้องเข้าถึงได้ (dialog, tabs, combobox)
- ฟอนต์ IBM Plex Sans Thai โฮสต์เอง, รองรับ prefers-reduced-motion, สัญลักษณ์คู่สี

**ส่วนหลังบ้าน (`apps/api`)**
- TypeScript บน Node.js LTS (ใช้รุ่น LTS ปัจจุบัน และอัปเกรดตามรอบ LTS)
- Fastify + REST API พร้อมเอกสาร OpenAPI สร้างจาก zod schema (ระบบอื่นเช่น n8n, GLPI, SBC Portal เรียกใช้ได้ตามมาตรฐาน)
- WebSocket สำหรับสถานะสด, fallback ดึงทุก 30 วินาที
- เข้าสู่ระบบ: OIDC กับ Google Workspace (บัญชี sb-school.ac.th) ในตัวแอป, บทบาทเก็บในฐานข้อมูล (ดูอย่างเดียว / รับเรื่อง / ผู้ดูแลทะเบียน)
- log: pino → promtail → Loki; ตัวชี้วัดแบบ Prometheus ที่ `/metrics` ให้ Zabbix/Grafana เฝ้าตัว NOC เอง

**ฐานข้อมูล (`packages/db`)**
- PostgreSQL 16 (`sbc-noc-db`)
- Drizzle ORM + drizzle-kit (SQL ชัดเจน, type จาก schema, migration เป็นไฟล์ SQL ใน Git ย้อนดูได้)
- ทุกการแก้ทะเบียนเขียน `audit_log`, ห้ามแก้ข้อมูลตรงใน production นอกจากผ่าน migration หรือหน้าจัดการ

**งานซิงก์ (`apps/worker`)**
- BullMQ บน Redis (`sbc-redis`) ตั้งเวลา ลองใหม่อัตโนมัติ และเก็บผลลง `sync_runs`
- ฐานข้อมูล → Zabbix: เขียน tag `building` `floor` `loc` `role` `uplink` (ฐานข้อมูลเป็นต้นทางเสมอ)
- Zabbix → ฐานข้อมูล: จับคู่ `zabbix_hostid`, รายงาน host ที่ยังไม่อยู่ในทะเบียน
- SBC ASSET → ฐานข้อมูล: รายการ LOC และจำนวนเครื่องห้องคอมฯ (อ่านอย่างเดียว)
- controller → ฐานข้อมูล: รายการ AP
- ส่วนหลังบ้านรวมเหตุตามต้นเหตุจาก `uplink` คู่กับ trigger dependencies ใน Zabbix, ตรวจความสดของข้อมูล (เกิน 2 นาทีแจ้งสถานะค้าง), token ของ Zabbix อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น แยก token อ่านกับ token รับเรื่อง

**ทดสอบและคุณภาพ**
- Vitest (unit), Testcontainers + PostgreSQL สำหรับทดสอบ migration และงานซิงก์บนฐานจริงชั่วคราว
- Playwright: end-to-end และถ่ายภาพ 3 ขนาด (1366, 1920, มือถือ 390) เทียบภาพทุกครั้งที่แก้
- ESLint + Prettier + typecheck ใน CI, Conventional Commits, เลขรุ่นแบบ SemVer
- Renovate (ทำงานกับ Gitea) เปิด PR อัปเดต dependency อัตโนมัติ ป้องกันไลบรารีเก่าค้าง
- ทดสอบความเร็วบนเครื่องจริงที่ต่อจอทีวี (เป้า ≥ 30 เฟรม/วินาที)

**deploy และดูแล**
- Docker multi-stage build แยก image `sbc-noc-web`, `sbc-noc-api`, `sbc-noc-worker` + container ฐานข้อมูล `sbc-noc-db` ใน compose เดียว
- network: `sbc-noc` ภายในสำหรับ api/worker/db และต่อเข้า network ที่มี `sbc-zabbix-web`, `sbc-redis`
- CI/CD: Gitea Actions (act_runner ตัวเดียวกับ SBC Portal ตาม ADR-007) lint → typecheck → test → build → push registry `git.sbc.lan` → deploy ด้วย compose pull ที่ `/opt/sbc-noc`; แยกสภาพแวดล้อม dev / prod แบบเดียวกับ SBC Portal
- ใช้งานเฉพาะใน LAN: ชื่อ `noc.sbc.lan` (DNS บน MikroTik) ผ่าน Nginx Proxy Manager พร้อม access list เฉพาะวงที่อนุญาต ไม่เปิดออกอินเทอร์เน็ต
- ติดตามตัว NOC: Zabbix web scenario เช็ก `/health`, `/metrics`, log ใน Loki, ดู container ด้วย Dozzle/Portainer

**โครงสร้าง repo `sbc/sbc-noc`** (รายละเอียดเต็มอยู่ใน `docs/architecture.md` ของ repo)

```
sbc-noc/
├─ apps/
│  ├─ web/        หน้าจอ React (M18–M22)
│  │  └─ src/ scene/ (ฉาก 3D แยกจาก React) panels/ admin/ lib/
│  ├─ api/        Fastify REST + WebSocket (M13–M17)
│  │  └─ src/ routes/ services/ status-engine/ zabbix/
│  └─ worker/     งานซิงก์ BullMQ (M05–M09, M11)
│     └─ src/ jobs/ connectors/ (zabbix, sbc-asset, unifi, omada, link)
├─ packages/
│  ├─ db/         schema Drizzle + migration + seed
│  ├─ shared/     zod schema, type, ค่าคงที่ (รหัสอาคาร, บทบาท)
│  └─ ui/         ชิ้นส่วนหน้าจอใช้ซ้ำ (เผื่อใช้ร่วมกับ Portal)
├─ infra/
│  ├─ compose/    compose dev/prod, sbc-noc-db, backup
│  ├─ zabbix/     template และสคริปต์ตั้งค่า (M10–M12)
│  └─ scripts/    สำรอง/กู้คืน, นำเข้าข้อมูลตั้งต้น
```

กติกาโครงสร้าง
- ทิศทางการเรียกใช้: `web` → `shared`, `ui` · `api` และ `worker` → `db`, `shared` · `packages` ห้ามเรียก `apps` · `web` ไม่เรียก `db` ตรง
- M01 สร้างเฉพาะชั้นบน (apps, packages, infra, docs, tests, workflows) แต่ละตัวมี README และโค้ดตั้งต้นเล็กที่สุดที่ build/test ผ่าน
- โฟลเดอร์ย่อยของแต่ละโมดูลสร้างตอนเริ่มโมดูลนั้น ไม่สร้างโฟลเดอร์ว่างล่วงหน้า
- เปลี่ยนโครงสร้างระดับบนต้องมี ADR

## 9. แผนงานแบ่งเป็น gate

แต่ละ gate ต้องผ่านเงื่อนไขปิดครบก่อนเริ่ม gate ถัดไป

**G0 ต้นแบบดีไซน์** (สถานะ: **ปิดแล้ว** 29 ก.ย. 2026)
- ขอบเขต: หน้า 3D ข้อมูลตัวอย่าง, baseline v1–v7
- เงื่อนไขปิด: ทีม 2–3 คนลองใช้โดยไม่อธิบายก่อน ทำงานหลักได้ (หาเหตุล่ม → บินไป → รับเรื่อง) และทดสอบบนจอทีวีจริงผ่าน

**G1 ทะเบียนในฐานข้อมูลพร้อม** (สถานะ: ยังไม่ปิด — ค้าง tag Zabbix ครบ 100% (M08 → M17), AP ครบ 132 (M06), ลำดับห้องหน้างาน)
- เชื่อม: PostgreSQL `sbc-noc-db`, Redis (คิวงาน), Adminer, SBC ASSET (อ่าน), Zabbix API (เขียน tag), รายการ AP จาก controller
- งาน: ตั้ง monorepo + CI พื้นฐาน, สร้าง container `sbc-noc-db` และ backup, schema และ migration (Drizzle), worker งานซิงก์ (BullMQ), นำเข้าข้อมูลตั้งต้นจาก Sheet (LOC 173, อุปกรณ์ 50), ตั้งลำดับเลข LOC ในฐานข้อมูล, นำเข้า AP 132 ตัว, กรอกลำดับห้องตามทางเดิน, งานซิงก์เขียน tag `building` `floor` `loc` `role` `uplink` ลง Zabbix, รายงานตรวจความครบ (IP ซ้ำ, uplink ชี้ไปอุปกรณ์ที่ไม่มี, ไม่มี LOC)
- เงื่อนไขปิด: รายงานตรวจความครบไม่มีข้อผิดพลาด, host เครือข่ายใน Zabbix มี tag ครบ 100% (รายการ "ไม่มีตำแหน่ง" เป็น 0), สำรองข้อมูล `sbc-noc-db` อยู่ในรอบ backup และทดลองกู้คืนได้

**G2 Zabbix พร้อมเป็นแหล่งข้อมูล** (สถานะ: ยังไม่ปิด — ค้าง M10, M11; M12 บางส่วน)
- เชื่อม: Zabbix (ตั้งค่า), MikroTik/สวิตช์ (SNMP)
- งาน: template ICMP ทุก host, SNMP บน CCR2116/CCR1036/SG6428X และพอร์ตไฟเบอร์ 8 เส้น, item PPPoE 4 ISP, trigger dependencies ตาม uplink, ผู้ใช้ API อ่านอย่างเดียว + ผู้ใช้สำหรับรับเรื่อง, แนวทางใช้ maintenance
- เงื่อนไขปิด: ทดลองปิดอุปกรณ์ต้นทาง 1 ตัวแล้ว Zabbix แสดงปัญหาเดียวที่ต้นเหตุ ลูกข่ายถูกพักแจ้งเตือน; traffic ไฟเบอร์และ ISP มีค่าจริง

**G3 backend sbc-noc (อ่านอย่างเดียว)** (สถานะ: ยังไม่ปิด — M13–M16 เสร็จบน dev; ค้าง M17 CI/CD + deploy)
- เชื่อม: Zabbix API, PostgreSQL `sbc-noc-db`, Redis, Loki, NPM, Gitea
- งาน: CI/CD เต็มรูปแบบ, REST API + OpenAPI อ่านทะเบียนและผังจากฐานข้อมูล, snapshot + WebSocket, รวมเหตุตามต้นเหตุ, ตรวจความสด, `/health`, unit test
- เงื่อนไขปิด: deploy บน sbc-ubuntu ใช้ได้ภายในวง management, snapshot ตรงกับ Zabbix, ข้อมูลช้าไม่เกิน 30 วินาที, ปิดพอร์ตที่เปิดตรงออกทุกวงแล้ว

**G4 หน้า 3D ต่อข้อมูลจริง** (สถานะ: **ปิดแล้ว** 5 ต.ค. 2026 — UAT ผ่าน, ทีวี 44 fps, ภาพ 3 ขนาดไม่มีข้อความเลยขอบ; ทดสอบบน dev ก่อนปิด G1–G3 ตาม ADR-0021 ตรวจซ้ำแบบย่อบน prod; จอ kiosk M34 ยังไม่ทำ)
- เชื่อม: sbc-noc (backend), Grafana, GLPI (ลิงก์ออก)
- งาน: ย้ายต้นแบบเป็น React + TypeScript + Vite (ฉาก 3D เป็นโมดูล Three.js แยก), อ่านผังและสถานะจาก API, หน้าจัดการทะเบียน, ย้ายสถานการณ์ตัวอย่างไปเป็นโหมดสาธิต (ADR-014) ไม่แสดงในหน้าจริง, จอทีวีแบบ kiosk (M34), เปิดปุ่ม Zabbix/Grafana/GLPI, Playwright ถ่ายภาพ 3 ขนาด
- เงื่อนไขปิด: UAT กับทีมผ่าน, จอทีวี ≥ 30 เฟรม/วินาที, ภาพหน้าจอ 3 ขนาดไม่มีข้อความเลยขอบ

**G5 การกระทำและสิทธิ์**
- เชื่อม: Zabbix API (event.acknowledge, maintenance.get), Google Workspace (OIDC)
- งาน: รับเรื่อง/แก้ไข/ยกเลิก บันทึกลง Zabbix, เข้าสู่ระบบด้วยบัญชี sb-school.ac.th, สิทธิ์ ดูอย่างเดียว / รับเรื่องได้, บันทึกการกระทำ
- เงื่อนไขปิด: รับเรื่องใน NOC แล้วเห็นใน Zabbix และกลับกัน, ผู้ไม่มีสิทธิ์รับเรื่องไม่ได้

**G6 แจ้งเตือนและต่อยอด**
- เชื่อม: n8n, UniFi/Omada/LINK controller, Metabase, GLPI API
- งาน: แจ้งเตือน LINE/Telegram, ความเร็วก้อนข้อมูลตาม traffic จริง, ผู้ใช้ Wi-Fi ต่อ AP, แถบเวลาย้อนดู, โหมดนอกเวลาเรียน, รายงาน
- เงื่อนไขปิด: กำหนดตามแต่ละฟีเจอร์เมื่อเริ่ม gate

รายละเอียดโมดูลทั้ง 39 ตัว (M00–M38) ผู้รับผิดชอบ ขนาด และเงื่อนไขเสร็จ อยู่ใน `sbc-noc-modules-by-gate-v2.md`

| ADR-013 | สภาพแวดล้อม | dev (เครื่องนักพัฒนา, compose + ข้อมูลทดสอบ), staging `noc-dev.sbc.lan`, prod `noc.sbc.lan`; dev และ staging ใช้ Zabbix token อ่านอย่างเดียว; การทดสอบที่เขียนเข้า Zabbix (tag, acknowledge, maintenance) ทำกับกลุ่ม host ทดสอบแยกเท่านั้น |
| ADR-014 | โหมดสาธิต | สถานการณ์ตัวอย่างจากต้นแบบเก็บเป็นชุดข้อมูลทดสอบของเครื่องคำนวณสถานะ และเป็นโหมดสาธิตสำหรับอบรม เปิดได้เฉพาะ dev/staging หรือผู้ดูแล มีป้าย "ข้อมูลสาธิต" ชัดเจน ไม่ปนกับข้อมูลจริง |
| ADR-015 | ออกรุ่นและย้อนกลับ | เลขรุ่น SemVer, image tag = รุ่น + git sha; migration เดินหน้าอย่างเดียว + backup อัตโนมัติก่อน migrate ทุกครั้ง; เปลี่ยนโครงตารางแบบ expand/contract (เพิ่มก่อน เลิกใช้ทีหลังในรุ่นถัดไป); ย้อนกลับ = ใช้ image รุ่นก่อน และกู้ backup เฉพาะเมื่อ migration ทำลายข้อมูล |
| ADR-016 | ความปลอดภัยในโค้ดและ CI | ตรวจ secret หลุด (gitleaks), ตรวจช่องโหว่ dependency (pnpm audit) และ image (Trivy), สร้าง SBOM; ป้องกัน branch main (ต้องผ่าน CI + PR); หน้าเว็บตั้ง CSP, rate limit, cookie ปลอดภัย; บัญชี Zabbix ของ NOC สิทธิ์น้อยที่สุดเฉพาะกลุ่ม host เครือข่าย |
| ADR-017 | เวลาและรูปแบบวันที่ | อุปกรณ์และเซิร์ฟเวอร์ทุกตัวซิงก์เวลา NTP จาก CCR2116 (สำคัญต่อการเรียงเหตุการณ์และหาต้นเหตุ); เก็บเวลาเป็น UTC แสดงผลเป็น Asia/Bangkok และปี พ.ศ. |

## 11. ข้อกำหนดที่ไม่ใช่ฟังก์ชัน (เป้าหมายที่ต้องวัดได้)

| หัวข้อ | เป้าหมาย |
|---|---|
| ความสดของสถานะ | เปลี่ยนใน Zabbix ถึงหน้าจอภายใน 30 วินาที (95% ของครั้ง); เกิน 2 นาทีแสดงสถานะค้าง |
| ความพร้อมใช้ของ NOC | 99% ในเวลาเรียน; ระบบล่มต้องรู้ภายใน 2 นาทีผ่าน Netwatch (ADR-010) |
| ความเร็ว | เปิดหน้าแรกใน LAN ≤ 3 วินาที; ภาพ 3D ≥ 30 เฟรม/วินาทีบนเครื่องจอทีวี, ≥ 20 บนโน้ตบุ๊ก |
| ขนาดระบบ | รองรับ 500 host ตอนเริ่ม และขยายเป็น 1,500 (รวมคอมพิวเตอร์) ได้โดยไม่แก้สถาปัตยกรรม |
| กู้คืนข้อมูล | ข้อมูลหายได้ไม่เกิน 24 ชั่วโมง (backup รายวัน); กู้ระบบกลับมาใช้ได้ภายใน 2 ชั่วโมง |
| เบราว์เซอร์ | Chrome และ Edge 2 รุ่นล่าสุด, Safari บน iPhone/iPad 2 รุ่นล่าสุด |
| การเข้าถึง | ข้อความและแผงต่างๆ ตามแนวทาง WCAG 2.1 ระดับ AA, สถานะใช้สีคู่สัญลักษณ์เสมอ |
| ภาษา | ภาษาไทยเป็นหลัก ชื่อเฉพาะทางเทคนิคคงภาษาอังกฤษ |
| ความปลอดภัย | ไม่มีพอร์ตเปิดนอก LAN, ทุกการกระทำมีบันทึก, ไม่มี secret ใน repo หรือฐานข้อมูล |
| ข้อมูลบุคคล (PDPA) | เก็บข้อมูลบุคลากรเท่าที่จำเป็น (รหัส ชื่อ อีเมล เบอร์สำหรับเวร) และใช้เฉพาะงาน NOC |

## 13. สิ่งที่ต้องเตรียมก่อนเริ่ม M01

- สิทธิ์ผู้ดูแลใน Gitea สำหรับสร้าง repo `sbc/sbc-noc` และตั้ง branch protection
- สิทธิ์แก้ config ของ act_runner (ค่า capacity ตาม ADR-007) และตรวจว่า image ของ runner มี Node LTS, pnpm, Docker
- บัญชีสำหรับ push image เข้า registry `git.sbc.lan` (เก็บเป็น Gitea secret)
- เครื่องที่รัน Claude Code เข้าถึง `192.168.1.6:3000` และ `git.sbc.lan` ได้
- ตกลงชื่อ staging `noc-dev.sbc.lan` และเพิ่ม DNS บน MikroTik (ใช้ตอน M17)
