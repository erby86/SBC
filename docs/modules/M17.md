# M17 — deploy และความปลอดภัยพื้นฐาน

ตาม modules-by-gate-v2: compose staging (`noc-dev.sbc.lan`) และ prod (`noc.sbc.lan`) ตาม ADR-0013, backup อัตโนมัติก่อน migrate (ADR-0015), สแกน image ด้วย Trivy, CSP/rate limit, proxy host ใน NPM (access list วง management), log เข้า Loki, Zabbix web scenario เช็ก `/health`, ปิดพอร์ตที่เปิดตรงออกทุกวง

**เสร็จเมื่อ:** เงื่อนไขปิด G3 ใน baseline ครบ — deploy บน sbc-ubuntu ใช้ได้ภายในวง management, snapshot ตรงกับ Zabbix, ข้อมูลช้าไม่เกิน 30 วินาที, ปิดพอร์ตที่เปิดตรงออกทุกวงแล้ว

**สถานะ:** โค้ดเสร็จ 2026-10-05 — รอผู้ใช้ทำขั้นบนเซิร์ฟเวอร์ (ข้างล่าง) แล้วรายงานผล

## สิ่งที่สร้าง

| ส่วน                                                                                                                                                                      | ที่อยู่                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| prod stack `sbc-noc-{db,api,worker,web,alloy}` — ไม่มี `ports:`, api/worker ใช้ role `noc_app` (DML อย่างเดียว), `DEMO_MODE`/`REGISTRY_EDIT` ปิด, Redis prefix `noc:`     | `infra/compose/compose.prod.yml`, `prod.env.example`  |
| deploy/rollback: build `<version>-<sha>` → Trivy + SBOM → backup → migrate → ตั้งรหัส `noc_app` → start → รอ health → บันทึกรุ่น; staging = backup → build → Trivy → up   | `infra/scripts/deploy.sh` (ADR-0022)                  |
| log ของ container `sbc-noc-*` ทั้ง prod และ staging → Loki เดิม (label `app="sbc-noc"`, `env`, `container`, `service`) ด้วย Grafana Alloy; log ในเครื่องจำกัดขนาด         | `infra/compose/alloy/config.alloy`                    |
| CSP ของหน้าเว็บ (ไม่มี `unsafe-eval`; Zod `jitless`), rate limit ต่อ client (api 10 req/s burst 40, WebSocket 30/นาที), IP จริงจาก `X-Real-IP` ของ NPM, nginx ไม่ใช่ root | `apps/web/nginx.conf.template`, `apps/web/Dockerfile` |
| e2e: `vite preview` ส่ง CSP เดียวกัน; ทุกหน้าจอล้มถ้ามีอะไรถูก CSP บล็อก; เทสต์ header CSP                                                                                | `apps/web/vite.config.ts`, `tests/e2e`                |
| CI job `scan`: Trivy lockfile + Dockerfile (HIGH/CRITICAL) + SBOM artifact `sbom`                                                                                         | `.gitea/workflows/build.yml`                          |

ทดสอบในเครื่องแล้ว: e2e 27/27 (CSP ไม่บล็อกอะไร), api + worker รันด้วย `noc_app` ได้ (61 ตารางเขียนได้), `\getenv` ตั้งรหัสบน psql 16 ได้, `deploy.sh` ผ่าน shellcheck และลองทั้ง flow ด้วย docker จำลอง (deploy, `--list`, `--rollback`) — **ยังไม่ได้รันกับ docker จริง** (ไม่มี docker ใน session)

## ขั้นบนเซิร์ฟเวอร์ (sbc-ubuntu) — ทำทีละก้อน

ก่อนเริ่ม: merge PR แล้วดึงเข้า `/opt/sbc-noc/src` ตาม `docs/runbooks/github-to-gitea.md`

### 1. staging ใช้ของใหม่ (nginx ไม่ใช่ root, CSP, rate limit)

```bash
cd /opt/sbc-noc/src && infra/scripts/deploy.sh staging
```

ควรเห็น `backup ok: …`, Trivy ไม่มีรายการ HIGH/CRITICAL, แล้ว `staging OK`; เปิด `http://noc-dev.sbc.lan` ใช้ได้เหมือนเดิม (ถ้า Trivy หยุด ให้ส่งผลมา อย่าใช้ `NO_SCAN=true` โดยไม่บันทึกเหตุผล)

ตรวจ CSP + rate limit:

```bash
curl -sI http://noc-dev.sbc.lan/ | grep -i content-security-policy
seq 1 100 | xargs -P 20 -I{} curl -s -o /dev/null -w '%{http_code}\n' http://noc-dev.sbc.lan/api/health | sort | uniq -c
```

ควรเห็น header `default-src 'self' …` และผลมีทั้ง `200` (ราว 40–60) และ `429` (ยิงพร้อมกันเกิน 10/s + burst 40) — หน้าเว็บปกติไม่ถึงเกณฑ์นี้

### 2. หา Loki

```bash
docker ps --format '{{.Names}}\t{{.Ports}}' | grep -i loki
docker inspect "$(docker ps --format '{{.Names}}' | grep -i loki | head -n 1)" --format '{{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}'
```

จดชื่อ container (เช่น `loki`) และ network — ใช้ใน `SBC_LOKI_NETWORK` และ `LOKI_URL=http://<ชื่อ container>:3100/loki/api/v1/push`

### 3. ไฟล์ env ของ prod

```bash
umask 077
cp /opt/sbc-noc/src/infra/compose/prod.env.example /opt/sbc-noc/prod.env
chmod 600 /opt/sbc-noc/prod.env
sed -i "s/^POSTGRES_PASSWORD=$/POSTGRES_PASSWORD=$(openssl rand -hex 24)/; s/^NOC_APP_PASSWORD=$/NOC_APP_PASSWORD=$(openssl rand -hex 24)/" /opt/sbc-noc/prod.env
# ค่าที่ใช้เหมือน dev (ไม่รวม ZABBIX_TOKEN_SYNC — prod ใช้ token แยก ข้อ 8)
for k in SBC_SHARED_NETWORK SBC_PROXY_NETWORK REDIS_URL ZABBIX_URL ZABBIX_TOKEN_READ \
  UNIFI_URL UNIFI_USERNAME UNIFI_PASSWORD UNIFI_SITE UNIFI_CA_FILE UNIFI_CONTROLLER_CODE \
  OMADA_URL OMADA_ID OMADA_CLIENT_ID OMADA_CLIENT_SECRET OMADA_SITE OMADA_CA_FILE OMADA_CONTROLLER_CODE \
  SBC_ASSET_CSV_URL LINK_ZABBIX_URL LINK_GRAFANA_URL LINK_GLPI_URL; do
  v="$(grep -m1 "^$k=" /opt/sbc-noc/dev.env | cut -d= -f2-)"
  [ -n "$v" ] || continue
  { grep -v "^$k=" /opt/sbc-noc/prod.env; printf '%s=%s\n' "$k" "$v"; } > /opt/sbc-noc/prod.env.new
  cat /opt/sbc-noc/prod.env.new > /opt/sbc-noc/prod.env
done
rm -f /opt/sbc-noc/prod.env.new
nano /opt/sbc-noc/prod.env    # ใส่ SBC_LOKI_NETWORK และ LOKI_URL จากข้อ 2; REDIS_PREFIX ต้องเป็น noc:
stat -c '%a %n' /opt/sbc-noc/prod.env
```

ควรเห็น `600 /opt/sbc-noc/prod.env`

### 4. ที่เก็บ backup ของ prod + cron (02:40 หลัง dev 02:30)

```bash
sudo mkdir -p /opt/sbc-backups/sbc-noc && sudo chown "$USER": /opt/sbc-backups/sbc-noc
( crontab -l 2>/dev/null; echo '40 2 * * * CONTAINER=sbc-noc-db DEST=/opt/sbc-backups/sbc-noc /opt/sbc-noc/src/infra/scripts/pg-backup.sh >> /opt/sbc-backups/sbc-noc/backup.log 2>&1' ) | crontab -
crontab -l | grep sbc-noc
```

### 5. deploy prod ครั้งแรก (สั่งนอกเวลาเรียน — build ใช้ CPU)

```bash
cd /opt/sbc-noc/src && infra/scripts/deploy.sh prod
```

ควรเห็นตามลำดับ: build 3 image, Trivy + `SBOM: /opt/sbc-noc/sbom/…`, `backup ok`, `migrations done: applied 2`, `sbc-noc-api: healthy`, `sbc-noc-web: healthy`, `sbc-noc-worker: running`, แล้ว `prod OK: 0.1.0-xxxxxxx`

ฐาน prod ว่าง ต้องนำเข้าข้อมูลตั้งต้นและตำแหน่ง (เหมือน M04/M19 บน dev):

```bash
docker run --rm --network sbc-noc-internal -v /opt/sbc-noc/src/infra/seed:/seed:ro \
  -e DATABASE_URL="postgres://sbc_noc:$(grep -m1 '^POSTGRES_PASSWORD=' /opt/sbc-noc/prod.env | cut -d= -f2-)@noc-db:5432/sbc_noc" \
  --entrypoint sh "sbc-noc-api:$(tail -n 1 /opt/sbc-noc/prod.releases | cut -d' ' -f2)" \
  -c 'node node_modules/@sbc-noc/db/dist/seed-cli.js /seed && node node_modules/@sbc-noc/db/dist/routes-cli.js /seed'
```

ควรเห็น `rows written this run: …` และ `placements written 45 of 45`, `routes written 12 of 12` (AP และ LOC จะตามมาเองจากงานซิงก์ใน worker)

### 6. NPM: proxy host `noc.sbc.lan`

ใน NPM → Hosts → Proxy Hosts → Add: Domain `noc.sbc.lan`, Scheme `http`, Forward Hostname `sbc-noc-web`, Port `80`, เปิด **Block Common Exploits** และ **Websockets Support**, Access List `sbc-noc-mgmt` (เหมือน `noc-dev.sbc.lan`)

### 7. ตรวจเงื่อนไขปิด G3

จากเครื่องในวง 192.168.1.x:

```bash
curl -s http://noc.sbc.lan/api/health/ready; echo
curl -sI http://noc.sbc.lan/ | grep -iE 'content-security-policy|x-frame'
curl -s http://noc.sbc.lan/api/status | python3 -c 'import sys,json,datetime as d; s=json.load(sys.stdin); t=d.datetime.fromisoformat(s["lastUpdate"].replace("Z","+00:00")); print("stale",s["stale"],"age",round((d.datetime.now(d.timezone.utc)-t).total_seconds()),"s")'
```

ควรเห็น `{"status":"ok",…}`, header CSP + X-Frame, `stale False age` ไม่เกิน 30 s (ลองหลายครั้ง); เทียบรายการเหตุในหน้า `http://noc.sbc.lan` กับ Problems ใน Zabbix ให้ตรงกัน; demo ต้องปิด: `curl -s -o /dev/null -w '%{http_code}\n' http://noc.sbc.lan/api/demo/scenarios` → `404`

จากเครื่องวงอื่น (เช่น Wi-Fi นักเรียน/ครู): `http://noc.sbc.lan` ต้องได้ `403`

พอร์ต: บน sbc-ubuntu

```bash
docker ps --filter name=sbc-noc- --format '{{.Names}}\t{{.Ports}}'
```

ทุกแถวต้องไม่มี `0.0.0.0:` หรือ `:::` (มีได้แค่ `80/tcp`, `3001/tcp`, `5432/tcp` ภายใน)

log: ใน Grafana → Explore → Loki: `{app="sbc-noc", env="prod"}` ต้องเห็น log ของ `sbc-noc-api`/`sbc-noc-worker`

### 8. Zabbix web scenario เช็ก `/health` (ทำใน UI ของ Zabbix)

1. Data collection → Hosts → Create host: ชื่อ `sbc-noc`, กลุ่ม `99-NOC-Test` (หรือกลุ่ม Applications ที่ใช้อยู่), ไม่ต้องมี interface
2. แท็บ Web scenarios ของ host → Create: Name `NOC health`, Update interval `1m`, Attempts `2`; Steps → Add: Name `ready`, URL `http://noc.sbc.lan/api/health/ready`, Required string `"status":"ok"`, Required status codes `200`
3. Triggers → Create: Name `NOC ใช้ไม่ได้`, Severity High, Expression `last(/sbc-noc/web.test.fail[NOC health])<>0`
4. ตรวจ: Monitoring → Latest data ของ host `sbc-noc` — `Failed step of scenario "NOC health"` = `0`

ถ้าได้ `403` แปลว่า Zabbix server เข้าผ่าน access list ไม่ได้ (ต้นทางเป็น IP ของ docker ไม่ใช่ 192.168.1.x): ดู IP ต้นทางใน log NPM (`docker logs sbc-npm --tail 20` หลัง Zabbix ยิง) แล้วเพิ่ม subnet นั้นใน access list `sbc-noc-mgmt` — แจ้งผลมาก่อนแก้ access list

### 9. (หลัง G2) tag Zabbix บน host จริง — ปิดค้างของ M08

ตาม ADR-0019: สร้าง token prod ของ `noc-api-sync` โดยให้ role มี Read-write เฉพาะกลุ่ม `01-`/`02-`/`03-` แล้วใส่ใน `prod.env` เป็น `ZABBIX_TOKEN_SYNC` และ `ZABBIX_TAG_GROUPS=<ชื่อกลุ่มคั่นด้วย ,>` จากนั้น `infra/scripts/deploy.sh prod --rollback <tag ปัจจุบัน>` (start ใหม่ด้วย env ใหม่ ไม่ build ซ้ำ) — tag ปัจจุบันดูจาก `infra/scripts/deploy.sh prod --list`

## ข้อจำกัด

- image อยู่ในเครื่องเท่านั้น (ADR-0022); push เข้า registry เมื่อ `git.sbc.lan` ใช้ https ได้
- `sbc-noc-alloy` อ่าน docker socket (แบบ read-only mount) เพื่ออ่าน log — กรองเฉพาะชื่อ `sbc-noc-*`
- runtime image ของ api/worker ลบ npm/corepack/yarn ที่มากับ `node:24-bookworm-slim` (ไม่ได้ใช้ตอนรัน และพา CVE ของ brace-expansion/tar/ip-address/undici มาเอง) และ `apt-get upgrade`; web ทำ `apk upgrade` และ `COPY --chmod=0644` ไฟล์ template ของ nginx (clone บนเซิร์ฟเวอร์อาจเป็น 600 ทำให้ user 101 อ่านไม่ได้ จน web unhealthy) — ถ้า Trivy เจอ CVE ใน base image อีก ให้ build ใหม่ด้วย `--pull` ก่อนเพิ่ม `.trivyignore`
- Trivy pin `0.74.0` (CI) และ `aquasec/trivy:0.74.0` (เซิร์ฟเวอร์) — อัปเดตทั้งสองที่พร้อมกัน
- prod ประกาศใช้กับทีม/จอทีวีหลัง G1–G2 ปิด (ADR-0021, ADR-0022)
