# M15 — เครื่องคำนวณสถานะ

ตาม modules-by-gate-v2: ดึง problem/item จาก Zabbix ทุก 30 วินาที, รวมกับทะเบียน, คำนวณต้นเหตุ/ขาดจากต้นทาง/บำรุงรักษา, ความสดข้อมูล, snapshot ใน Redis, unit test ครอบคลุมกรณีต้นแบบทั้ง 4 สถานการณ์

**เสร็จเมื่อ:** snapshot ตรงกับ Zabbix; เกิน 2 นาทีไม่ได้ข้อมูลแสดงสถานะค้าง

## การทำงาน

| ไฟล์                                   | หน้าที่                                                                                                        |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `apps/worker/src/connectors/zabbix.ts` | เพิ่ม `problems()` (problem.get + trigger.get หา host) และ `hostsInMaintenance()` (host.get + maintenance.get) |
| `apps/worker/src/status/engine.ts`     | `inputFromZabbix()` แปลงข้อมูล Zabbix → input; `createStatusEngine().tick()` → `computeStatus` (M38) → Redis   |
| `apps/worker/src/main.ts`              | รันทุก `STATUS_POLL_MS` (30 s) แบบไม่ซ้อนรอบ — ไม่ใช้คิว BullMQ เพื่อไม่ให้ sync.runs โต 2,880 แถว/วัน         |
| `apps/api/src/routes/status.ts`        | `GET /status` อ่าน snapshot จาก Redis, ตรวจความสดซ้ำ (worker ตาย → ค้าง), `Cache-Control: no-store`            |

กติกา:

- host → อุปกรณ์ ผ่าน `core.external_refs` (zabbix, จาก M08); host ที่ไม่อยู่ในทะเบียนข้าม (อยู่ในรายการ unmatched_host แล้ว)
- ความรุนแรง: High/Disaster = ล่ม, Warning/Average = เตือน, Information/Not classified = ไม่นับ
- หลาย problem บนอุปกรณ์เดียว → เลือกที่แรงสุด (เก่าสุดในระดับนั้น) ข้อความต่อท้าย "(+N ปัญหา)"
- รับเรื่องใน Zabbix (acknowledged) → `ack` (ผู้รับ `zabbix:<userid>` + ข้อความล่าสุด)
- host ใน maintenance → บำรุงรักษา (รวมอุปกรณ์ข้างใต้)
- Zabbix อ่านไม่ได้ → ใช้ข้อมูลรอบก่อนพร้อม `lastUpdate` เดิม → เกิน 2 นาทีเป็น `stale`
- Redis: key `<REDIS_PREFIX>status:snapshot`, ประกาศทาง channel `<REDIS_PREFIX>status:updates` (ให้ M16 WebSocket)
- อุปกรณ์ใต้ตัวที่ล่มที่รายงาน ping ล่มเองด้วยจะเป็นเหตุของตัวเอง — M11 (trigger dependency) จะทำให้ Zabbix ไม่ส่งปัญหาซ้ำแบบนี้

ทดสอบ: ทั้ง 4 สถานการณ์ของ M38 เล่นเป็นข้อมูล Zabbix (problem, ack, maintenance) แล้วได้ผลเท่ากับ fixture; `stale` = Zabbix ล่ม 6 นาทีแล้ว snapshot ค้างพร้อมข้อมูลเดิม; ฐานจริง: problem บน c1036 → เหตุที่ต้นเหตุ, ข้างใต้ขาดจากต้นทาง; api — 503 ก่อนมี snapshot, ค้างเมื่อ snapshot เก่า
