# M35 — เฝ้าตัวเอง

ตาม modules-by-gate-v2: Netwatch บน CCR2116 ตรวจ sbc-ubuntu และ `/health` ส่ง Telegram ตรงจากเราเตอร์ (ADR-0010); item ใน Zabbix เฝ้าคิว worker ค้างและงานซิงก์ล้ม

**เสร็จเมื่อ:** ปิด container NOC ทดลองแล้วได้ Telegram ภายใน 2 นาที; งานซิงก์ล้มขึ้นเป็นปัญหาใน Zabbix

**สถานะ:** โค้ดเสร็จ รอทำขั้นบนเซิร์ฟเวอร์ เราเตอร์ และ Zabbix (ด้านล่าง)

## การตัดสินใจในโมดูลนี้ (ปรับจาก ADR-0010)

- `/metrics` อยู่ที่ **api** (`/api/metrics` ผ่าน NPM) ไม่ใช่ worker: worker ไม่มีพอร์ต HTTP และ M17 ปิดพอร์ตที่เปิดตรงทั้งหมด api อ่านค่าของ worker จาก Redis (heartbeat, ตัวนับคิว) และจาก `sync.runs`
- ฝั่งเราเตอร์ใช้ **script + scheduler ทุก 30 วินาที** แทนการตั้ง Netwatch: script เดียวตรวจทั้ง ping เซิร์ฟเวอร์และ `/api/health/ready` (ตรวจทั้ง URL และเนื้อหา `"status":"ok"`) แล้วส่ง Telegram ครั้งเดียวต่อเหตุ และส่งอีกครั้งเมื่อกลับปกติ
- งานที่ค้างสถานะ `running` เพราะ worker ถูกปิดกลางทาง (เช่นตอน deploy) worker จะเปลี่ยนเป็น `interrupted` ตอนเริ่ม ไม่นับเป็นงานล้มและไม่ค้างเป็นงานค้าง

| `NOC ข้อมูลสถานะค้างเกิน 2 นาที`        | Warning | snapshot เก่ากว่า 120 วินาทีตลอด 3 นาที                             |
| `NOC งานซิงก์ล้ม: <งาน>`                | Average | ครั้งล่าสุดของงานล้มตลอด 3 นาที (ลองใหม่สำเร็จภายใน 3 นาทีไม่เตือน) |
| `NOC งานซิงก์ค้างเกิน 1 ชั่วโมง: <งาน>` | Warning | งานรันค้างเกิน 3600 วินาทีตลอด 10 นาที                              |

ทดสอบในเครื่อง: unit test (api 4, worker 3) + int test บน PostgreSQL 16 + Redis จริง (`readSyncHealth`, `interrupted`, `--fail-test`, ตัวนับคิวจาก BullMQ จริง); `pnpm lint/depcruise/typecheck/test/build/format:check` ผ่าน — **ยังไม่ได้ import template ใน Zabbix จริงและยังไม่ได้รัน script บนเราเตอร์จริง**

## ขั้นบนเซิร์ฟเวอร์ — ทำทีละก้อน

ก่อนเริ่ม: merge PR แล้วดึงเข้า `/opt/sbc-noc/src` ตาม `docs/runbooks/github-to-gitea.md`

### 1. deploy staging แล้ว prod

```bash
cd /opt/sbc-noc/src && infra/scripts/deploy.sh staging && infra/scripts/deploy.sh prod
```

ตรวจ (ควรเห็น `noc_worker_up 1` และแถว `noc_sync_job_last_failed{job="..."}` ต่องาน):

```bash
curl -s http://noc.sbc.lan/api/metrics | grep -E '^noc_(worker_up|selfmon|queue|status|sync_job_last_failed)'
```

### 2. Zabbix: import template แล้วผูกกับ host `sbc-noc`

1. Data collection → Templates → Import → เลือกไฟล์ `infra/zabbix/templates/sbc-noc-selfmon.yaml` → Import
2. Data collection → Hosts → `sbc-noc` → แท็บ Templates → Link `SBC NOC self-monitoring` → Update
3. ตรวจหลัง 2–3 นาที: Monitoring → Latest data, host `sbc-noc`, ชื่อขึ้นต้น `NOC` — `NOC worker up` = `1` และมี `NOC sync <งาน>: last attempt failed` ครบทุกงาน (registry-stats, zabbix-match, …)

### 3. เราเตอร์ CCR2116: script ส่ง Telegram

ต้องมี bot token และ chat id ของ Telegram (เก็บบนเราเตอร์เท่านั้น ไม่ใส่ใน git)

1. ทดสอบก่อนว่าเราเตอร์เปิด NOC ได้ (เราเตอร์ต้องอยู่ในวง 192.168.1.x ตาม access list `sbc-noc-mgmt`) — ควรเห็น `"status":"ok"`:

   ```
   :put ([/tool fetch url="http://noc.sbc.lan/api/health/ready" output=user as-value]->"data")
   ```

2. วางเนื้อหาทั้งไฟล์ `infra/mikrotik/noc-watch.rsc` ใน Terminal ของเราเตอร์
3. System → Scripts → `noc-watch` → แก้ `PASTE_BOT_TOKEN` และ `PASTE_CHAT_ID` → OK
4. ทดสอบส่ง Telegram (ควรได้ข้อความ `test` และไม่มี error):

   ```
   /tool fetch url="https://api.telegram.org/bot<TOKEN>/sendMessage" http-method=post http-header-field="Content-Type: application/json" http-data="{\"chat_id\":\"<CHAT>\",\"text\":\"test\"}" output=none check-certificate=yes
   ```

   ถ้าขึ้น error เรื่องใบรับรอง หยุดแล้วส่ง error มา (เราเตอร์ยังไม่มี CA ที่ใช้ตรวจ api.telegram.org)

5. Log ของเราเตอร์ต้องไม่มี `noc-watch:` ขึ้นทุก 30 วินาที (มีแปลว่าตรวจไม่ผ่าน)

### 4. ทดสอบเงื่อนไขเสร็จ

ปิด NOC ชั่วคราว (ผู้ใช้จะเห็นหน้าเว็บล่มประมาณ 2 นาที):

```bash
docker stop sbc-noc-web; sleep 120; docker start sbc-noc-web
```

ผลที่ควรเห็น: Telegram `SBC NOC: http://noc.sbc.lan/api/health/ready is failing (NOC down)` ภายใน 2 นาทีหลัง stop และ `SBC NOC: back to normal` หลัง start

งานซิงก์ล้ม (`zabbix-match` รันทุก 15 นาที จึงค้างสถานะล้มนานพอให้ Zabbix เห็น):

```bash
docker exec sbc-noc-worker node dist/run-job-cli.js --fail-test zabbix-match
```

ผลที่ควรเห็น: ภายใน 3–5 นาที Monitoring → Problems มี `NOC งานซิงก์ล้ม: zabbix-match`; ปิดเองเมื่อรอบถัดไปสำเร็จ (สั่งเองได้ด้วย `docker exec sbc-noc-worker node dist/run-job-cli.js zabbix-match`)

## ข้อจำกัด

- เกณฑ์ (3 นาที, 10 นาที, 1 ชั่วโมง) ตั้งจากรอบงานปัจจุบัน ปรับได้ใน template ใน Zabbix
- `/api/metrics` เปิดให้วง management เหมือน `/api/health` (ไม่มีข้อมูลลับ: ชื่องาน ตัวนับ และอายุเป็นวินาที)
- งานที่ไม่ได้รันเกิน 7 วันจะหายจาก discovery (item ถูกลบตาม lifetime ของ LLD)
- ข้อความ Telegram เป็นภาษาอังกฤษ เพราะเลี่ยงปัญหาการเข้ารหัสอักษรไทยใน script ของ RouterOS
