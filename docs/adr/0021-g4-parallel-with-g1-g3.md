# ADR-0021: ทำและปิด G4 บน dev ขนานกับ G1–G3

- **สถานะ:** Accepted
- **วันที่:** 2026-10-05

## บริบท

baseline-v8 ข้อ 9 กำหนดให้แต่ละ gate ผ่านเงื่อนไขปิดครบก่อนเริ่ม gate ถัดไป แต่งานโค้ด G1–G3 เสร็จเร็ว สิ่งที่ค้างไม่ใช่โค้ด แต่เป็นข้อมูลและการตั้งค่าภายนอก ได้แก่ tag Zabbix ครบ 100% (M08 → M17), AP ครบ 132 ตัว (M06), ลำดับห้องหน้างาน, M10/M11 ใน Zabbix และ deploy prod (M17) ทั้งหมดต้องรอคนทำหรือรอหน้างาน

ระหว่างนั้น G4 (M18–M22) ทำต่อบน dev ด้วยข้อมูลจริงที่มีอยู่ (ADR-0020 กำหนดลำดับโมดูลใน G4) และผ่านเงื่อนไขปิดแล้วเมื่อ 5 ต.ค. 2026 (UAT ผ่าน, จอทีวี 44 fps, ภาพ 3 ขนาดไม่มีข้อความเลยขอบ — M22) ADR-0020 อนุมัติเฉพาะลำดับโมดูลภายใน G4 ยังไม่มีการตัดสินใจเรื่องทำ G4 ก่อนปิด G1–G3

## การตัดสินใจ

- ยอมรับให้ G4 ทำและปิดบน dev (`noc-dev.sbc.lan`) ขนานกับ G1–G3 ได้ — ผลปิด G4 วันที่ 5 ต.ค. 2026 ใช้ได้
- **prod (`noc.sbc.lan`) เปิดให้ใช้ได้ก็ต่อเมื่อ G1, G2, G3 ปิดครบแล้ว** และผ่าน M17
- เมื่อ G1–G3 ปิด ให้ตรวจ G4 ซ้ำบน prod แบบย่อ: เทสต์ Playwright (`E2E_BASE_URL` ชี้ staging ที่ใช้ข้อมูลชุดเดียวกับ prod) และ fps บนจอทีวีจริง — ไม่ต้องทำ UAT กับทีมใหม่ ยกเว้นหน้าจอเปลี่ยน
- gate อื่นยังใช้กติกาข้อ 9 ตามเดิม การทำ gate ใดก่อน gate ก่อนหน้าปิดต้องมี ADR

## ผลที่ตามมา

- งานหน้าจอไม่ต้องรอข้อมูลหน้างาน ทีมได้ลองใช้และให้ความเห็นเร็วขึ้น
- ความเสี่ยง: ภาพบน dev ยังไม่ครบ (host ไม่มี tag, AP ยังไม่มีตำแหน่ง) ผู้ใช้อาจเข้าใจว่าระบบพร้อมแล้ว — ลดด้วยการไม่เปิด prod จนกว่า G1–G3 ปิด และแสดงรายการ "ไม่มีตำแหน่ง" บนหน้าจอ
- ความเสี่ยง: ข้อมูลจริงที่เพิ่มภายหลังอาจทำให้ข้อความยาวขึ้นจนเลยขอบ — ลดด้วยการตรวจซ้ำบน prod ตามข้างบน
