# M35 — เฝ้าตัวเอง

ตาม modules-by-gate-v2: Netwatch บน CCR2116 ตรวจ sbc-ubuntu และ `/health` ส่ง Telegram ตรงจากเราเตอร์ (ADR-0010; ใช้ Discord webhook แทน); item ใน Zabbix เฝ้าคิว worker ค้างและงานซิงก์ล้ม

**เสร็จเมื่อ:** ปิด container NOC ทดลองแล้วได้ Telegram (ใช้ Discord แทน) ภายใน 2 นาที; งานซิงก์ล้มขึ้นเป็นปัญหาใน Zabbix

**สถานะ:** เสร็จ 2026-10-06 (ผู้ใช้ยืนยันบน prod)

## ผลบน prod (2026-10-06)

- ปิด `sbc-noc-web` 2 นาที: Discord ได้ `SBC NOC: http://noc.sbc.lan/api/health/ready is failing (NOC down)` เวลา 11:24 (ภายใน 2 นาทีหลัง stop) และ `SBC NOC: back to normal` หลัง start
- Zabbix trigger `NOC ใช้ไม่ได้` (High, host `sbc-noc`) เกิด 11:24:01 ปิดเอง 11:26:01
- เราเตอร์: ติดตั้ง script ด้วย `/import`, URL webhook อยู่ใน script `noc-watch-url`, ตัวนับการล้มอยู่ใน comment ของ script `noc-watch`
- ผู้ใช้ยืนยันผ่านเงื่อนไขเสร็จทั้งสองข้อ (งานซิงก์ล้มทดสอบด้วย `--fail-test` ตามข้อ 4)
- ปัญหาที่เจอระหว่างทางและแก้แล้ว: รุ่นแรกเก็บตัวนับใน global variable ซึ่งไม่คงอยู่ข้ามรอบที่ scheduler รัน (log `check 1` ทุกรอบ จึงไม่เคยถึงครั้งที่ 2 ที่ส่ง Discord) → เก็บใน comment ของ script แทน; `\;     \n` ที่เห็นใน log ตอนเพิ่ม script เป็นรูปแบบที่ RouterOS แสดงขึ้นบรรทัดใหม่ ไม่ใช่ source เพี้ยน; log แต่ละบรรทัดขึ้นซ้ำ 2 ครั้ง (เลข `*11` เดียวกัน) มาจากกฎ `/system logging` ไม่ใช่ scheduler 2 ตัว

## การตัดสินใจในโมดูลนี้ (ปรับจาก ADR-0010)

- `/metrics` อยู่ที่ **api** (`/api/metrics` ผ่าน NPM) ไม่ใช่ worker: worker ไม่มีพอร์ต HTTP และ M17 ปิดพอร์ตที่เปิดตรงทั้งหมด api อ่านค่าของ worker จาก Redis (heartbeat, ตัวนับคิว) และจาก `sync.runs`
- ฝั่งเราเตอร์ใช้ **script + scheduler ทุก 30 วินาที** แทนการตั้ง Netwatch: script เดียวตรวจทั้ง ping เซิร์ฟเวอร์และ `/api/health/ready` (ตรวจทั้ง URL และเนื้อหา `"status":"ok"`) แล้วส่ง Discord ครั้งเดียวต่อเหตุ และส่งอีกครั้งเมื่อกลับปกติ
- งานที่ค้างสถานะ `running` เพราะ worker ถูกปิดกลางทาง (เช่นตอน deploy) worker จะเปลี่ยนเป็น `interrupted` ตอนเริ่ม ไม่นับเป็นงานล้มและไม่ค้างเป็นงานค้าง

## ขั้นบนเซิร์ฟเวอร์ — ทำทีละก้อน

ก่อนเริ่ม: merge PR แล้วดึงเข้า `/opt/sbc-noc/src` ตาม `docs/runbooks/github-to-gitea.md`

### 1. deploy staging แล้ว prod

```bash
cd /opt/sbc-noc/src && infra/scripts/deploy.sh staging && infra/scripts/deploy.sh prod
```

ตรวจ (ควรเห็น `noc_worker_up 1` และแถว `noc_sync_job_last_failed{job="..."}` ต่องาน):

```bash
curl -s http://noc.sbc.lan/api/metrics | grep -E '^noc_(worker_up|selfmon|queue|status|sync_job_last_failed)'
```

### 2. Zabbix: import template แล้วผูกกับ host `sbc-noc`

Zabbix อ่าน NOC ตรงที่ `http://sbc-noc-web` ผ่าน docker network `sbc-net` (prod web อยู่บน network นี้ด้วย): ถ้าเรียกผ่าน `noc.sbc.lan` คำขอจะเข้า NPM จาก IP ของ docker (`172.22.x`) และ access list `sbc-noc-mgmt` ตอบ `403`

1. Data collection → Templates → Import → เลือกไฟล์ `infra/zabbix/templates/sbc-noc-selfmon.yaml` → Import (import ซ้ำได้ ค่าเดิมถูกอัปเดต)
2. Data collection → Hosts → คลิก `sbc-noc` → แท็บ **Host** ช่อง **Templates** → Select → group `Templates/Applications` → `SBC NOC self-monitoring` → Update
3. host `sbc-noc` → แท็บ **Macros** → Host macros → Add `{$NOC.URL}` = `http://sbc-noc-web` → Update — ตั้งที่ host เสมอ: import template ซ้ำไม่อัปเดตค่า macro ที่มีอยู่แล้ว (dev 2026-10-06 ค้างเป็น `http://noc.sbc.lan` แล้วได้ 403 จาก NPM `openresty`)
4. web scenario `NOC health` จาก M17: step `ready` → URL `http://sbc-noc-web/api/health/ready`, Required status codes `200` (เดิมเรียกผ่าน NPM ได้ `403` แต่ยังนับว่าผ่านเพราะช่อง status codes ว่าง)
5. ตรวจหลัง 2–3 นาที: Monitoring → Latest data, host `sbc-noc`, ชื่อขึ้นต้น `NOC` — `NOC worker up` = `1` และมี `NOC sync <งาน>: last attempt failed` ครบทุกงาน (registry-stats, zabbix-match, …)

### 3. เราเตอร์ CCR2116: script ส่ง Discord

ช่องทางแจ้งเตือนเป็น Discord webhook (ผู้ใช้เลือกแทน Telegram 2026-10-06): สร้างที่ Discord → Server Settings → Integrations → Webhooks → New Webhook → เลือก channel → Copy Webhook URL — URL นี้เก็บบนเราเตอร์เท่านั้น ไม่ใส่ใน git (ใครมี URL ก็โพสต์เข้า channel ได้)

**ติดตั้งด้วย `/import`** ไม่คัดวางเนื้อ script ลง Terminal: import ซ้ำได้ (ลบ script/scheduler `noc-watch` เดิมทุกตัวแล้วสร้างใหม่) และ URL webhook อยู่ใน `noc-watch-url` จึงไม่หาย

1. ทดสอบก่อนว่าเราเตอร์เปิด NOC ได้ (เราเตอร์ต้องอยู่ในวง 192.168.1.x ตาม access list `sbc-noc-mgmt`) — ควรเห็น `"status":"ok"`; ถ้าขึ้น error หยุดแล้วส่งข้อความมา:

   ```
   :put ([/tool fetch url="http://noc.sbc.lan/api/health/ready" output=user as-value]->"data")
   ```

2. เก็บ URL webhook ใน script แยก `noc-watch-url` (ทำครั้งเดียว; import ซ้ำไม่ลบ) — ถ้ามีอยู่แล้วใช้ `set` แทน `add`:

   ```
   /system script add name=noc-watch-url policy=read source="<WEBHOOK_URL>"
   ```

3. ทดสอบส่ง Discord (ควรเห็นข้อความ `test` ใน channel และ `status: finished`):

   ```
   /tool fetch url=[/system script get [find name=noc-watch-url] source] http-method=post http-header-field="Content-Type: application/json" http-data="{\"content\":\"test\"}" output=none check-certificate=yes
   ```

   ถ้าขึ้น error เรื่องใบรับรอง หยุดแล้วส่ง error มา (เราเตอร์ยังไม่มี CA ที่ใช้ตรวจ discord.com)

4. ดาวน์โหลด `infra/mikrotik/noc-watch.rsc` (ปุ่ม Raw/Download ใน Gitea) → Winbox → Files → ลากไฟล์วาง → Terminal:

   ```
   /import file-name=noc-watch.rsc verbose=yes
   ```

   ควรจบด้วย `Script file loaded and executed successfully`; import ลบ script/scheduler `noc-watch` เดิมทุกตัว (รวมตัวที่ซ้ำ) แล้วสร้างใหม่

5. ตรวจ:

   ```
   /system scheduler print where on-event~"noc-watch"
   /system script run noc-watch
   /log print where message~"noc-watch"
   ```

   ควรเห็น scheduler แถวเดียว, `script run` ไม่มี error, และ log ไม่มี `noc-watch:` ใหม่ (มีแปลว่าตรวจไม่ผ่าน — ท้ายบรรทัดบอกเหตุ: `ping lost`, `fetch error` หรือ `not ok: <เนื้อหา>`)

### 4. ทดสอบเงื่อนไขเสร็จ

ปิด NOC ชั่วคราว (ผู้ใช้จะเห็นหน้าเว็บล่มประมาณ 2 นาที):

```bash
docker stop sbc-noc-web; sleep 120; docker start sbc-noc-web
```

ผลที่ควรเห็น: Discord `SBC NOC: http://noc.sbc.lan/api/health/ready is failing (NOC down)` ภายใน 2 นาทีหลัง stop และ `SBC NOC: back to normal` หลัง start

งานซิงก์ล้ม (`zabbix-match` รันทุก 15 นาที จึงค้างสถานะล้มนานพอให้ Zabbix เห็น):

```bash
docker exec sbc-noc-worker node dist/run-job-cli.js --fail-test zabbix-match
```

ผลที่ควรเห็น: ภายใน 3–5 นาที Monitoring → Problems มี `NOC งานซิงก์ล้ม: zabbix-match`; ปิดเองเมื่อรอบถัดไปสำเร็จ (สั่งเองได้ด้วย `docker exec sbc-noc-worker node dist/run-job-cli.js zabbix-match`)

## ข้อจำกัด

- เกณฑ์ (3 นาที, 10 นาที, 1 ชั่วโมง) ตั้งจากรอบงานปัจจุบัน ปรับได้ใน template ใน Zabbix
- `/api/metrics` เปิดให้วง management เหมือน `/api/health` (ไม่มีข้อมูลลับ: ชื่องาน ตัวนับ และอายุเป็นวินาที) และให้ container บน `sbc-net` (Zabbix, Loki, Grafana) เปิด `sbc-noc-web` ได้โดยไม่ผ่าน access list — ไม่มีพอร์ตเปิดออกนอกเครื่อง
- Zabbix ไม่ผ่าน NPM จึงไม่เห็นเมื่อ NPM ล่ม — script บนเราเตอร์ตรวจผ่าน `noc.sbc.lan` จึงครอบคลุมกรณีนั้น
- งานที่ไม่ได้รันเกิน 7 วันจะหายจาก discovery (item ถูกลบตาม lifetime ของ LLD)
- ข้อความ Discord เป็นภาษาอังกฤษ เพราะเลี่ยงปัญหาการเข้ารหัสอักษรไทยใน script ของ RouterOS
